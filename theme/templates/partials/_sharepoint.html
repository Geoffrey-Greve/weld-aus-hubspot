{# ───────────────────────────────────────────────────────────────────────────── _sharepoint.html - SharePoint share-link normaliser (QA #46) ───────────────────────────────────────────────────────────────────────────── Problem: SharePoint "share" links in the /:b:/s// format route through SharePoint's guest-access *preview* page. On Android (Chrome + in-app webviews) that page hands off to the OneDrive/SharePoint app or shows a Microsoft sign-in interstitial instead of serving the file - even with ?download=1 appended. Fix: rewrite site-scoped share links to SharePoint's direct-download endpoint, which returns the file bytes with Content-Disposition: attachment and skips the preview UI / app handoff: https://.sharepoint.com/::/s//? -> https://.sharepoint.com/sites//_layouts/15/download.aspx?share= Anything that is not a site-scoped SharePoint share link (plain URLs, HubSpot file links, personal OneDrive /g/ links, empty values, or already-rewritten download.aspx URLs) is returned unchanged, so the macro is safe to wrap around every resource URL and is idempotent. IMPORTANT CAVEAT: this only helps when the share is anonymous ("Anyone with the link"). If the file is shared "People in with the link", the Microsoft login is mandatory and no URL rewrite can bypass it - the share must be reconfigured or the file rehosted (e.g. on HubSpot File Manager).
