{# _module-session-resolve.html Resolves ONE course-module booking URL into the session behind it, so a module row can be rendered with its real dates and price instead of a bare name. Why this exists: course_modules (the HubDB table) carries only a name, an order and a booking URL - no date, no price. Everything a buyer needs to choose between modules already exists, but it lives on the `courses` or `events` row that the booking URL points at, and until now only the checkout tunnel ever looked it up. So the course page asked people to tick boxes with no idea what each tick cost or when it ran, and they found out one page later. PARITY IS LOAD-BEARING, not tidiness. The checkout sends each selected module's displayed price as `expectedUnitCents`, and the worker's per-module guard is the same DIRECTIONAL `comparePriceQuote` the single-session path uses (packages/worker/src/routes/reserve.ts): it refuses only a price resolving ABOVE what this page displayed. So the failure direction is a page price that is too LOW - which is exactly what an unresolved or zero price is, and why the caller still refuses to make such a row selectable. The caller therefore refuses to make a module selectable until it has resolved a price above zero: an unpriced tickbox is a checkout that cannot complete. This mirrors the primary resolution path in theme/modules/checkout-tunnel.module/module.html (the `module_session_ids` block) - same id parsing, same courses-before-events precedence, same ticket_types_json price resolution. The page must never quote a number the checkout then disagrees with; that is defect 213's whole family. The checkout's extra fallbacks (hs_id__eq / id__eq / a 250-row scan) are deliberately NOT copied: they are a per-module table scan on a page that renders many modules, and their only effect here would be to make an already-degraded row render a price. A row this partial cannot resolve degrades to its own booking link, which is the same place it went before. RESOLUTION ORDER: the module's HubSpot PRODUCT ID first, its booking URL second. events-engine migration 0031 says it outright - "The Course Modules HubDB table identifies a module by its HubSpot Product ID" - and the Worker stores that id on the child event so a course page can find the session "without inferring it from a title". The CMS never used it, so every module needed `/checkout/?session_id=` typed by hand into `module_booking_url`, and on production all 44 rows had none: the entire selector rendered "Contact to book". The join is HubDB to HubDB, server-side: a `courses` row carrying the same `module_product_id` IS the module's session. That keeps the checkbox value a HubDB row id (what `/checkout/` resolves), keeps the Worker pricing that same row through `hubdb-pricing.ts` (which finds it by `worker_event_id`, migration 0035), and needs no Worker call from this page at all. Reading the Worker's `ticket_types.price_cents` instead would put a SECOND price source back on the module path, which is the exact fault 0035 removed. A module taught in several sittings matches several rows. The soonest one still on sale wins; if none is, the soonest overall is kept so the row still renders with its badge rather than vanishing. Letting the buyer CHOOSE between sittings is the parent-pickable problem in CLAUDE.md § 7.7 and is deliberately not attempted here. Inputs travel on the `module_session_input` NAMESPACE, set before the include: module_session_input.url - the raw course_modules.module_booking_url module_session_input.product_id - course_modules.hubspot_product_id, matched against courses.module_product_id module_session_input.tier - the visitor's resolved member tier, or '' when they are not entitled to a member rate A namespace rather than two plain variables because the caller resolves modules inside a {% for %} loop: a namespace attribute assigned in a loop body is visible to the include by construction, where a loop-local {% set %} depends on include scoping that would only fail server-side on upload. Output: the `module_session` namespace - found, source ('courses'|'events'), resolved_by ('product'|'url'|''), id, name, location, start_date, end_date, date_label, member_price, non_member_price, worker_event_id, member_ticket_type_id, non_member_ticket_type_id, bookable, members_only, status, has_started, off_sale, off_sale_label `bookable` gates on worker_event_id ALONE, matching the checkout's own gate for a selected module. It deliberately does not also require use_event_engine: that flag routes a row's OWN Register CTA (CLAUDE.md § 11.5), and the selected-module checkout never reads it, so requiring it here would hide modules the checkout would happily reserve. `off_sale` is the courses row's own `status` column saying Cancelled or Sold Out - which CLAUDE.md § 7.6 makes an EDITORIAL decision no live read may reverse - OR the session's start date having passed. `off_sale_label` says which, because "Sold out" invites a waitlist enquiry and "Registrations closed" does not. Every other surface that offers a session already honours it - the corporate bulk booking panel excludes both, the course cards badge them - and the module selector did not, so a cancelled module kept its tickbox and went into the basket beside live ones. Reported separately from `bookable` because the two are different facts: an off-sale module is still a resolved, priced session and still shows its dates, it just cannot be bought today.
